When one processor must make a sound and read buttons at the same time, each job delays the other. The tone clicks while the program checks a button, or a press is missed while the program makes the tone. The RP2040 has two processor cores, so each job can have a core of its own. The difficulty then moves to another place: the two cores share one memory, and data that both of them change can be damaged with no error message. In this lesson Core 0 makes the audio samples and Core 1 reads four buttons. You send commands from one core to the other through a hardware queue, and you protect shared data with a lock. #Multicore #DualCore #RP2040

## What We Are Building

<Card title="Dual-Core Tone Synthesizer" icon="star">
A two-core audio synthesizer. Core 0 generates a square wave or a sawtooth wave at the frequency of a note and sends it to a piezo buzzer through PWM. Core 1 scans four push buttons and sends note commands to Core 0 through the FIFO, a small hardware queue between the cores (first in, first out). A mutex, a lock that only one core can hold at a time, protects a shared settings struct. The tone stays clean while you press buttons, because each job has its own core.

## RP2040 Dual-Core Architecture

<InArticleAd />


The RP2040 contains two ARM Cortex-M0+ cores running at 125 MHz. At reset, only Core 0 runs. Core 1 sleeps until you start it. Your `main()` function runs on Core 0.

Both cores see the same flash, the same RAM and the same peripherals, and nothing stops one core from writing where the other is working. This makes it easy to pass data: both cores can use the same variable. It is also the danger. Think of two clerks who update one paper ledger. Each reads the balance, adds a payment, and writes the new balance. If both read before either writes, one payment is lost. Two cores that change one variable lose updates in the same way, and the program shows no error.

So the rule for this lesson is: data that both cores change needs one of three tools. The inter-core FIFO passes short messages from one core to the other. A spinlock protects a few instructions. A mutex protects an update that takes longer.

### Launching Core 1

You give `multicore_launch_core1()` the name of a function, and Core 1 starts to run that function:

```c
#include "pico/multicore.h"

void core1_entry(void) {
    /* This runs on Core 1 */
    while (true) {
        /* Core 1 work goes here */
    }
}

int main() {
    stdio_init_all();

    multicore_launch_core1(core1_entry);

    /* Continue running on Core 0 */
    while (true) {
        /* Core 0 work goes here */
    }
}
```

The function you pass to `multicore_launch_core1()` must never return. If it does, Core 1 will enter a fault state. Always write it as an infinite loop.

### Stack and Memory

The stack is the memory where a function keeps its local variables. Each core needs its own, or the two would overwrite each other. The default Core 1 stack size is 2 KB (`PICO_CORE1_STACK_SIZE` defaults to `PICO_STACK_SIZE`, which is 0x800). If your Core 1 function uses large local arrays or functions that call themselves, you can increase it up to 4 KB, the size of the RAM bank that holds this stack. Define `PICO_CORE1_STACK_SIZE` for the whole build in `CMakeLists.txt`, because the stack is allocated inside the SDK's own source file and a `#define` in your `main.c` does not reach it:

```cmake
target_compile_definitions(multicore_synth PRIVATE PICO_CORE1_STACK_SIZE=4096)
```

Either core can reach global and static variables, so these are the ones that need protection. Local variables live on each core's own stack and need none.

## Inter-Core FIFO

<InArticleAd />


The safest way to share data is not to share it: one core puts a message in a queue and the other takes it out. The hardware takes care that a message is never half written. The RP2040 has two such queues, one for each direction. Each holds up to 8 messages of 32 bits. To push is to put a message in. To pop is to take the oldest message out.

```text
 ┌──────────────┐  queue, 8 words  ┌──────────────┐
 │   Core 0     │                  │   Core 1     │
 │  (waveform   │ push         pop │  (button     │
 │   generator) ├─────────────────>│   scanner)   │
 │              │                  │              │
 │              │ pop         push │              │
 │              │<─────────────────┤              │
 └──────────────┘  queue, 8 words  └──────────────┘
```

```c
#include "pico/multicore.h"

/* On Core 0: send a value to Core 1 */
multicore_fifo_push_blocking(42);

/* On Core 1: receive the value from Core 0 */
uint32_t value = multicore_fifo_pop_blocking();
/* value is now 42 */
```

A blocking call stops the calling core until it can finish: a push waits while the FIFO is full, and a pop waits while it is empty. A core that must keep to a schedule cannot wait like this, so there are calls that give up or only look:

```c
/* Returns true if a value was successfully pushed (FIFO not full) */
bool success = multicore_fifo_push_timeout_us(42, 1000);

/* Returns true if a value was available (FIFO not empty) */
uint32_t value;
bool available = multicore_fifo_rvalid();  /* Check without popping */
if (available) {
    value = multicore_fifo_pop_blocking();
}
```

In the synthesizer, Core 1 pushes one 32-bit word that holds both the note frequency and the waveform type. Core 0 pops these commands and changes its audio output.

### FIFO Limitations

The FIFO holds only 8 words. If the sender pushes faster than the receiver pops, the FIFO fills and a blocking push stops the sender. So use the FIFO for commands that are sent now and then. For a steady flow of data, use shared memory with a lock.

## Spinlocks

<InArticleAd />


A statement such as `shared_counter++` looks like one action, but the processor does it in three: load the value, add 1, store the result. If the other core does the same three steps in between, one update is lost:

```text
   shared_counter = 5 at the start
 ┌───────────────────┐  ┌───────────────────┐
 │ Core 0            │  │ Core 1            │
 │ 1. load  (gets 5) │  │                   │
 │                   │  │ 2. load  (gets 5) │
 │ 3. add 1 (has 6)  │  │                   │
 │                   │  │ 4. add 1 (has 6)  │
 │ 5. store 6        │  │                   │
 │                   │  │ 6. store 6        │
 └───────────────────┘  └───────────────────┘
   shared_counter = 6: one addition is lost
```

A lock prevents this. A core takes the lock, does its three steps, and releases the lock. The other core must wait until then. The piece of code between taking and releasing is called the critical section.

The lock itself must not have the same weakness, so the RP2040 builds it in hardware. It has 32 spinlocks (SIO_SPINLOCK0 through SIO_SPINLOCK31). Reading a spinlock register tests the lock and takes it in one step that nothing can split (an atomic step). If the lock was free, the read returns nonzero and the caller now owns it. If the lock was already held, the read returns zero.

The Pico SDK wraps this in a few calls:

```c
#include "hardware/sync.h"

/* Claim a spinlock (the SDK tracks which are available) */
int spin_lock_num = spin_lock_claim_unused(true);
spin_lock_t *lock = spin_lock_init(spin_lock_num);

/* Acquire the lock (spins until available, disables interrupts) */
uint32_t saved_irq = spin_lock_blocking(lock);

/* Critical section: safe to access shared data */
shared_counter++;

/* Release the lock (restores interrupts) */
spin_unlock(lock, saved_irq);
```

When a core calls `spin_lock_blocking()`, two things happen:

- Interrupts are disabled on that core. Without this, an interrupt handler on the same core could ask for the lock that its own core already holds, and wait for ever. This is a deadlock.
- The core reads the spinlock register again and again (it "spins") until the lock is free.

The returned `saved_irq` value is passed to `spin_unlock()`, which puts the interrupts back as they were.

### When to Use Spinlocks

Use a spinlock when the critical section is a few instructions long. The waiting core does no useful work while it spins, and the holding core has its interrupts off, so never hold a spinlock during a long calculation or while you wait for a device.

The Pico SDK keeps some spinlock numbers for its own use. Always ask for a free one with `spin_lock_claim_unused()` and do not write a spinlock number into your code.

## Mutex

<InArticleAd />


A mutex (from "mutual exclusion") is a lock for work that takes longer. It is built from a spinlock, but the spinlock is held only for the few instructions that record which core owns the mutex. A core that finds the mutex taken does not spin with its interrupts off. It rests until the owner releases the mutex (the `WFE` instruction, wait for event) and then tries again.

```c
#include "pico/mutex.h"

mutex_t config_mutex;

void setup(void) {
    mutex_init(&config_mutex);
}

void update_config(void) {
    mutex_enter_blocking(&config_mutex);

    /* Safe to modify shared configuration */
    synth_config.frequency = 440;
    synth_config.waveform = WAVE_SQUARE;

    mutex_exit(&config_mutex);
}
```

A core that makes sound cannot wait for a lock: every sample it sends late is heard. For such a loop there is `mutex_try_enter()`, which returns at once and says whether it got the lock:

```c
if (mutex_try_enter(&config_mutex, NULL)) {
    /* Got the lock, update config */
    synth_config.frequency = new_freq;
    mutex_exit(&config_mutex);
}
/* If the lock was held, skip the update and try again next iteration */
```

In the synthesizer, the mutex protects the shared settings struct. Core 1 writes the waveform setting after a long press, and Core 0 reads it on every audio sample with `mutex_try_enter()`.

## The Synthesizer Project

<InArticleAd />


The work is divided by how urgent it is. Core 0 writes a new sample to the PWM about every 62 microseconds. Core 1 scans the buttons every 20 ms, which also hides contact bounce.

### Note Definitions

Each button plays one note. A FIFO message is one 32-bit word, so two macros pack the frequency into its lower 16 bits and the waveform into its upper 16 bits, and two more take them out again:

```c
#define NOTE_C4   262   /* Hz */
#define NOTE_E4   330
#define NOTE_G4   392
#define NOTE_C5   523

/* Pack note and waveform into a single 32-bit FIFO message */
#define MAKE_CMD(freq, wave)  (((uint32_t)(wave) << 16) | (uint32_t)(freq))
#define CMD_FREQ(cmd)         ((cmd) & 0xFFFF)
#define CMD_WAVE(cmd)         (((cmd) >> 16) & 0xFFFF)
```

### Waveform Types

```c
typedef enum {
    WAVE_SQUARE = 0,
    WAVE_SAWTOOTH = 1,
} waveform_t;
```

## Waveform Generation

<InArticleAd />


A pin can only be high or low, but sound needs levels in between. PWM (pulse width modulation) gives them: the pin switches much faster than anyone can hear, and the fraction of the time it is high (the duty cycle) sets the average voltage. The buzzer cannot follow the fast switching, so it moves with the average. Core 0 computes a new level, called a sample, 16,000 times a second and writes it to the PWM.

### PWM as Audio Output

The PWM counter counts from 0 to the wrap value and starts again. Here it wraps at 250, which gives a PWM frequency of 500 kHz and 250 possible levels:

```c
#include "hardware/pwm.h"

#define AUDIO_PIN      18
#define PWM_WRAP       250    /* PWM counter wraps at 250 */
#define SAMPLE_RATE    16000  /* 16 kHz audio sample rate */

void audio_pwm_init(void) {
    gpio_set_function(AUDIO_PIN, GPIO_FUNC_PWM);
    uint slice = pwm_gpio_to_slice_num(AUDIO_PIN);

    pwm_config config = pwm_get_default_config();
    pwm_config_set_wrap(&config, PWM_WRAP - 1);
    pwm_config_set_clkdiv(&config, 1.0f);  /* Full speed */
    pwm_init(slice, &config, true);

    pwm_set_gpio_level(AUDIO_PIN, 0);
}
```

With a 125 MHz system clock and a wrap value of 250, the PWM frequency is $125\ \text{MHz} / 250 = 500\ \text{kHz}$, far above what the ear can hear. The level goes from 0 to 249, which is close to 8 bits of resolution.

### Waveform Sample Computation

To make a note, the program must know where it is inside one cycle of the wave. It keeps this position in a 16-bit number called the phase: 0 is the start of a cycle and 65,535 is its end. For every sample it adds a fixed step to the phase. A 16-bit number that passes 65,535 starts again at 0, and this is the start of the next cycle. A larger step passes through the cycle faster, so the note is higher. This counter is called a phase accumulator. The step for a frequency $f$ in Hz is

$$
\text{step} = \frac{f \times 65536}{\text{sample rate}}
$$

For C4, $262 \times 65536 / 16000 = 1073$ (the fraction is dropped).

```c
static volatile uint32_t current_freq = NOTE_C4;
static volatile waveform_t current_wave = WAVE_SQUARE;

/* Phase accumulator: 16-bit fixed-point (0 to 65535 = one full cycle) */
static uint16_t phase = 0;
static uint16_t phase_step = 0;

void update_phase_step(void) {
    /* phase_step = (frequency * 65536) / sample_rate */
    phase_step = (uint16_t)((uint32_t)current_freq * 65536 / SAMPLE_RATE);
}

uint8_t compute_sample(void) {
    phase += phase_step;

    switch (current_wave) {
        case WAVE_SQUARE:
            return (phase < 32768) ? (PWM_WRAP - 1) : 0;

        case WAVE_SAWTOOTH:
            return (uint8_t)((phase * (PWM_WRAP - 1)) >> 16);

        default:
            return 0;
    }
}
```

The square wave is at the full level for the first half of each cycle (phase below 32,768) and at zero for the second half. The sawtooth rises in a straight line from 0 to the full level, in step with the phase. Both come from the same phase, so a new note needs only a new step.

## Circuit Connections

<InArticleAd />


Each button connects a pin to GND. The internal pull-up resistors hold the pins high, so a pressed button reads low.

```text
 ┌──────────────────┐
 │  Raspberry Pi    │
 │  Pico            │
 │                  │
 │  GP10 ├─┤BTN1├── GND  (C4: 262 Hz)
 │  GP11 ├─┤BTN2├── GND  (E4: 330 Hz)
 │  GP12 ├─┤BTN3├── GND  (G4: 392 Hz)
 │  GP13 ├─┤BTN4├── GND  (C5: 523 Hz)
 │       (internal pull-ups)
 │                  │
 │  GP18 ├──── Piezo (+)
 │   GND ├──── Piezo (-)
 │                  │
 │      USB         │
 └───────┤├─────────┘
```

### Speaker Wiring

If you use a small 8 ohm speaker in place of the piezo, put a 100 ohm resistor in series to limit the current. An RP2040 pin can supply about 12 mA. That is enough for a small piezo buzzer and too little to drive a speaker loudly.

### Waveform Toggle

Hold Button 4 for more than 1 second and release it: the waveform changes between square and sawtooth.

## Complete Firmware

<InArticleAd />


```c title="main.c"
#include <stdio.h>
#include "pico/stdlib.h"
#include "pico/multicore.h"
#include "pico/mutex.h"
#include "hardware/pwm.h"
#include "hardware/timer.h"

/* ---- Configuration ---- */

#define AUDIO_PIN       18
#define PWM_WRAP        250
#define SAMPLE_RATE     16000

#define BTN_C4_PIN      10
#define BTN_E4_PIN      11
#define BTN_G4_PIN      12
#define BTN_C5_PIN      13

#define NOTE_C4         262
#define NOTE_E4         330
#define NOTE_G4         392
#define NOTE_C5         523

#define DEBOUNCE_MS     20
#define LONG_PRESS_MS   1000

/* Pack command: low 16 bits = frequency, high 16 bits = waveform */
#define MAKE_CMD(freq, wave)  (((uint32_t)(wave) << 16) | (uint32_t)(freq))
#define CMD_FREQ(cmd)         ((cmd) & 0xFFFF)
#define CMD_WAVE(cmd)         (((cmd) >> 16) & 0xFFFF)

typedef enum {
    WAVE_SQUARE = 0,
    WAVE_SAWTOOTH = 1,
    WAVE_COUNT
} waveform_t;

/* ---- Shared state (protected by mutex) ---- */

typedef struct {
    uint32_t frequency;
    waveform_t waveform;
    bool note_on;
} synth_config_t;

static mutex_t config_mutex;
static synth_config_t shared_config = {
    .frequency = NOTE_C4,
    .waveform = WAVE_SQUARE,
    .note_on = false
};

/* ---- Audio output (Core 0) ---- */

static uint16_t phase = 0;
static uint16_t phase_step = 0;

void audio_pwm_init(void) {
    gpio_set_function(AUDIO_PIN, GPIO_FUNC_PWM);
    uint slice = pwm_gpio_to_slice_num(AUDIO_PIN);

    pwm_config config = pwm_get_default_config();
    pwm_config_set_wrap(&config, PWM_WRAP - 1);
    pwm_config_set_clkdiv(&config, 1.0f);
    pwm_init(slice, &config, true);
    pwm_set_gpio_level(AUDIO_PIN, 0);
}

uint8_t compute_sample(waveform_t wave) {
    phase += phase_step;

    switch (wave) {
        case WAVE_SQUARE:
            return (phase < 32768) ? (PWM_WRAP - 1) : 0;

        case WAVE_SAWTOOTH:
            return (uint8_t)((phase * (uint32_t)(PWM_WRAP - 1)) >> 16);

        default:
            return 0;
    }
}

void core0_audio_loop(void) {
    /* Period between samples in microseconds */
    const uint32_t sample_period_us = 1000000 / SAMPLE_RATE;

    uint32_t local_freq = NOTE_C4;
    waveform_t local_wave = WAVE_SQUARE;
    bool local_note_on = false;

    while (true) {
        /* Check for commands from Core 1 via FIFO */
        if (multicore_fifo_rvalid()) {
            uint32_t cmd = multicore_fifo_pop_blocking();

            if (cmd == 0) {
                /* Note off command */
                local_note_on = false;
            } else {
                local_freq = CMD_FREQ(cmd);
                local_wave = (waveform_t)CMD_WAVE(cmd);
                phase_step = (uint16_t)((uint32_t)local_freq * 65536 / SAMPLE_RATE);
                local_note_on = true;
                phase = 0;  /* Reset phase for clean note start */
            }
        }

        /* Also check mutex-protected config for waveform changes */
        /* try_enter never waits: if Core 1 holds the lock, keep the old value */
        if (mutex_try_enter(&config_mutex, NULL)) {
            local_wave = shared_config.waveform;
            mutex_exit(&config_mutex);
        }

        /* Output sample */
        if (local_note_on) {
            uint8_t sample = compute_sample(local_wave);
            pwm_set_gpio_level(AUDIO_PIN, sample);
        } else {
            pwm_set_gpio_level(AUDIO_PIN, 0);
        }

        busy_wait_us(sample_period_us);
    }
}

/* ---- Button scanning (Core 1) ---- */

typedef struct {
    uint gpio;
    uint32_t frequency;
    bool last_state;
    uint32_t press_start_ms;
    bool pressed;
} button_t;

static button_t buttons[4];

void buttons_init(void) {
    uint pins[4] = {BTN_C4_PIN, BTN_E4_PIN, BTN_G4_PIN, BTN_C5_PIN};
    uint32_t freqs[4] = {NOTE_C4, NOTE_E4, NOTE_G4, NOTE_C5};

    for (int i = 0; i < 4; i++) {
        buttons[i].gpio = pins[i];
        buttons[i].frequency = freqs[i];
        buttons[i].last_state = false;
        buttons[i].press_start_ms = 0;
        buttons[i].pressed = false;

        gpio_init(pins[i]);
        gpio_set_dir(pins[i], GPIO_IN);
        gpio_pull_up(pins[i]);
    }
}

void core1_entry(void) {
    buttons_init();

    waveform_t current_wave = WAVE_SQUARE;
    bool any_pressed = false;

    while (true) {
        any_pressed = false;

        for (int i = 0; i < 4; i++) {
            bool raw = !gpio_get(buttons[i].gpio);  /* Active low with pull-up */

            if (raw && !buttons[i].pressed) {
                /* Button just pressed */
                buttons[i].pressed = true;
                buttons[i].press_start_ms = to_ms_since_boot(get_absolute_time());

                /* Send note-on command through FIFO */
                uint32_t cmd = MAKE_CMD(buttons[i].frequency, current_wave);
                multicore_fifo_push_blocking(cmd);
            }

            if (!raw && buttons[i].pressed) {
                /* Button released */
                uint32_t held_ms = to_ms_since_boot(get_absolute_time()) - buttons[i].press_start_ms;
                buttons[i].pressed = false;

                /* Long press on button 4 toggles waveform */
                if (i == 3 && held_ms >= LONG_PRESS_MS) {
                    current_wave = (waveform_t)((current_wave + 1) % WAVE_COUNT);

                    /* Update shared config through mutex */
                    mutex_enter_blocking(&config_mutex);
                    shared_config.waveform = current_wave;
                    mutex_exit(&config_mutex);

                    printf("Waveform: %s\n",
                           current_wave == WAVE_SQUARE ? "square" : "sawtooth");
                }
            }

            if (buttons[i].pressed) {
                any_pressed = true;
            }
        }

        /* If no buttons are pressed, send note-off */
        if (!any_pressed) {
            /* Only send note-off if FIFO is not full, to avoid blocking */
            if (multicore_fifo_wready()) {
                multicore_fifo_push_blocking(0);  /* 0 = note off */
            }
        }

        sleep_ms(DEBOUNCE_MS);
    }
}

/* ---- Main ---- */

int main() {
    stdio_init_all();
    mutex_init(&config_mutex);
    audio_pwm_init();

    printf("Dual-Core Tone Synthesizer\n");
    printf("Buttons: GP10=C4, GP11=E4, GP12=G4, GP13=C5\n");
    printf("Long-press GP13 to toggle waveform\n");

    /* Launch button scanner on Core 1 */
    multicore_launch_core1(core1_entry);

    /* Core 0 runs the audio loop (never returns) */
    core0_audio_loop();

    return 0;  /* Never reached */
}
```

### How the Cores Cooperate

Follow one button press through the program:

<Steps>
1. Core 1 scans the buttons every 20 ms. When it finds a new press, it packs the note frequency and the waveform type into one 32-bit command and pushes it to the FIFO.

2. Core 0 runs the audio loop. At the top of each pass it asks whether the FIFO holds a command (`multicore_fifo_rvalid()`). Only then does it pop, so the pop never waits. It takes the frequency and waveform out of the command and computes the new phase step.

3. Core 0 computes the next sample from the phase and writes it to the PWM, which drives the piezo buzzer.

4. After a long press on Button 4, Core 1 also writes the new waveform into the shared struct, inside the mutex. Core 0 reads the struct with `mutex_try_enter()`, so it never waits for the lock.
</Steps>

In both cases the audio core only looks and never waits.

4. Connect the Pico in BOOTSEL mode: hold the BOOTSEL button while plugging in the USB cable. The Pico appears as a USB mass storage device.

5. Copy the firmware to the Pico:
   ```bash
   cp multicore_synth.uf2 /media/$USER/RPI-RP2/
   ```
   On macOS the mount point is `/Volumes/RPI-RP2/`. On Windows, drag the file to the RPI-RP2 drive in File Explorer.

6. The Pico reboots automatically. Press the buttons to play notes. Long-press Button 4 to toggle between square and sawtooth waveforms. Open a serial monitor (115200 baud) to see waveform change messages.
</Steps>

## Summary

<InArticleAd />


The RP2040 runs two jobs at the same time, one on each core. Here Core 0 keeps the audio timing and Core 1 works at the speed of a hand on a button. The cores share one memory, so data that both change needs a rule:

- Send short commands through the inter-core FIFO, which holds 8 words of 32 bits.
- Protect a few instructions with a spinlock, and a longer update with a mutex.
- In a loop that must keep its timing, only look: `multicore_fifo_rvalid()` and `mutex_try_enter()` never wait.
- Keep shared data small and hold a lock for as short a time as you can.

The next step is to move data with no processor work at all: see [DMA and high-speed data pipelines](/education/embedded-programming-rpi-pico/dma-high-speed-data-pipelines/).
