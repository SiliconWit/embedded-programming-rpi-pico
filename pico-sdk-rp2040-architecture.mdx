A new microcontroller board does nothing until you can put your own program on it, and on many boards that first step costs a day: a programmer to buy, a driver to install, a build that fails with no clear reason. The Raspberry Pi Pico needs only a USB cable. In this lesson you install the Pico SDK (software development kit: the libraries and build scripts for the board), see what is inside its RP2040 chip and how the chip starts, and build a first project: a Pico that a computer accepts as a keyboard and that types a message when you plug it in. Every later project in the course uses the same build and loading steps. #PicoSDK #RP2040 #EmbeddedSystems

## RP2040 Architecture

<InArticleAd />


The RP2040 is the microcontroller on the Pico. Its parts answer three questions that come up in every project: why can two things run at once, where does the program live, and why can a bad program never lock you out of the board? In the drawing, the flash memory is a separate chip on the board; everything else is inside the RP2040.

```text
 ┌────────────┐          ┌────────────┐
 │   Core 0   │          │   Core 1   │
 │ Cortex-M0+ │          │ Cortex-M0+ │
 └─────┬──────┘          └──────┬─────┘
       └────────────┬───────────┘
 ┌──────────────────┴─────────────────┐
 │  Bus fabric: joins every part      │
 └──┬─────────┬────────┬─────────┬────┘
 ┌──┴───┐  ┌──┴───┐  ┌─┴────┐ ┌──┴─────────┐
 │ SRAM │  │Flash │  │ DMA  │ │ Peripherals│
 │264 KB│  │ 2 MB │  │12 ch.│ │USB PIO ADC │
 └──────┘  └──────┘  └──────┘ └────────────┘
```

### Dual Cortex-M0+ Cores

A core is a processor: the part that runs your instructions. The RP2040 has two ARM Cortex-M0+ cores at up to 133 MHz each, so two pieces of code can run at the same moment. Your program starts on core 0; core 1 sleeps until your code calls the SDK function `multicore_launch_core1()`.

Both cores see the same memory and peripherals (the built-in hardware blocks such as USB, timers and the ADC). Each has its own stack, the memory where a running function keeps its local data.

The Cortex-M0+ has no floating-point unit, so `float` arithmetic runs as software routines, much slower than integer arithmetic.

### Memory: 264 KB SRAM in 6 Banks

SRAM is the working memory: your variables live there, and it is empty at every power-up. Two cores sharing one memory block would often wait for each other, so the 264 KB is six separate banks: four of 64 KB and two of 4 KB.

In the region programs normally use (0x20000000 to 0x2003FFFF), the four large banks are striped: each 32-bit word goes to the next bank in turn, so two cores reading in the same clock cycle usually reach different banks and neither waits. The two 4 KB banks often hold the stacks of core 0 and core 1.

### Bus Fabric (AHB-Lite Crossbar)

The bus fabric carries every read and write between the parts that ask (the two cores, and the DMA controller, which copies data without the processor) and the parts that answer (the SRAM banks, the flash and the peripherals). AHB-Lite is the ARM bus standard it uses.

It works like a telephone exchange: any caller reaches any line, and calls to different lines run at the same time. Core 0 can read SRAM bank 0 while core 1 writes bank 2 and DMA writes bank 1, all in one clock cycle. Only two requests for the same part in the same cycle make one of them wait.

### Boot Process

Boot is what the chip does between power-up and the first line of your `main()`. Its first stage is the reason a bad program cannot lock a Pico.

<Steps>
1. **ROM bootloader (inside the chip).** The RP2040 has 16 KB of mask ROM at address 0x00000000: memory fixed when the chip was made, which no program can change. The chip always starts here, and the ROM looks for a valid program in the flash chip. If BOOTSEL is held during power-up, or the flash holds no valid program, the ROM presents the Pico to the computer as a USB drive that accepts a UF2 file.

2. **Second-stage boot (in flash).** The first 256 bytes of the flash hold a small program that the SDK adds for you. It sets the flash chip up for XIP (execute in place): the processor runs code directly from flash and does not copy it to SRAM first.

3. **Your application.** The processor reads the vector table (the list of start addresses at the beginning of your program), runs the start-up code of the SDK, and then calls your `main()`.
</Steps>

UF2 (USB Flashing Format) makes loading by copy possible. A `.uf2` file is your program cut into blocks, each marked with the flash address where it belongs; the ROM writes each block there and restarts the chip. It is like parcels that each carry their own delivery address.

## CMakeLists.txt

<InArticleAd />


A Pico program is built from your files and hundreds of SDK files, each with its own compiler options, so nobody types the commands by hand. CMake reads `CMakeLists.txt`, which names your project, your source files and the SDK libraries you use, and writes the build instructions; `make` then runs the compiler. TinyUSB is the USB library that comes with the SDK. This is the smallest file for a TinyUSB keyboard:

```cmake
cmake_minimum_required(VERSION 3.13)

# Pull in the Pico SDK (must come before project())
include(pico_sdk_import.cmake)

project(usb_text_injector C CXX ASM)
set(CMAKE_C_STANDARD 11)
set(CMAKE_CXX_STANDARD 17)

# Initialize the SDK
pico_sdk_init()

add_executable(usb_text_injector
    main.c
    usb_descriptors.c
)

# Link the TinyUSB device library and standard SDK libraries
target_link_libraries(usb_text_injector
    pico_stdlib
    tinyusb_device
    tinyusb_board
)

# Include the current directory for tusb_config.h
target_include_directories(usb_text_injector PRIVATE ${CMAKE_CURRENT_SOURCE_DIR})

# Create UF2 output alongside ELF
pico_add_extra_outputs(usb_text_injector)
```

Key points about this file:

- `pico_sdk_init()` must be called after `project()` and before `add_executable()`.
- `add_executable()` lists every source file of the program. A `.c` file that is in the folder but not in this list is not compiled.
- `target_link_libraries()` names the SDK libraries the program uses. `tinyusb_device` and `tinyusb_board` are TinyUSB built for the RP2040.
- The compiler produces an `.elf` file. `pico_add_extra_outputs()` also produces the `.uf2` file that you copy to the Pico.

## UF2 Flashing

<InArticleAd />


To flash a board is to write a program into its flash memory. On the Pico you copy a file, and the ROM bootloader does the writing:

```text
 ┌──────────┐ hold BOOTSEL ┌──────────┐ copy  ┌──────────┐
 │   Pico   │ and plug in  │ RPI-RP2  │ .uf2  │   Pico   │
 │ unplugged├─────────────>│USB drive ├──────>│ restarts,│
 └──────────┘              └──────────┘       │ runs it  │
                                              └──────────┘
```

<Steps>
1. Unplug the Pico from USB.

2. Hold down the BOOTSEL button (the white button on the board).

3. While holding BOOTSEL, plug the Pico into your computer via USB.

4. Release BOOTSEL. The Pico appears as a USB drive named `RPI-RP2`.

5. Drag (or copy) the `.uf2` file onto the `RPI-RP2` drive.

6. The Pico writes the program to flash, removes the drive, and restarts into your application.
</Steps>

On Linux, the drive usually mounts under `/media/$USER/RPI-RP2`. On macOS it appears on the desktop and in `/Volumes/RPI-RP2`. On Windows it appears as a new drive letter in File Explorer.

:::tip
Because the bootloader is in ROM, this works even after a program that stops at once: hold BOOTSEL, plug in, and load a new one. A debug probe on the SWD (Serial Wire Debug) pins can also flash the board without unplugging it.
:::

## TinyUSB HID Keyboard Configuration

<InArticleAd />


When a USB device is plugged in, the computer asks it what it is, and the device answers with descriptors: small blocks of data in a fixed format. This exchange is called enumeration. If the answer says "keyboard", the computer loads its own keyboard driver, and nothing needs to be installed. Two files hold the answers: `tusb_config.h` and `usb_descriptors.c`.

### tusb_config.h

This header tells TinyUSB which device classes to build: only HID is on (1); serial port (CDC), storage (MSC), MIDI and vendor are off (0).

```c
#ifndef TUSB_CONFIG_H
#define TUSB_CONFIG_H

/* Board and MCU configuration (RP2040) */
#define CFG_TUSB_MCU          OPT_MCU_RP2040
#define CFG_TUSB_OS           OPT_OS_PICO

/* USB device configuration */
#define CFG_TUD_ENABLED       1
#define CFG_TUD_HID           1
#define CFG_TUD_CDC           0
#define CFG_TUD_MSC           0
#define CFG_TUD_MIDI          0
#define CFG_TUD_VENDOR        0

/* HID buffer size */
#define CFG_TUD_HID_EP_BUFSIZE 16

#endif /* TUSB_CONFIG_H */
```

### usb_descriptors.c

This file holds the descriptors. The device descriptor gives the identity: a vendor number and a product number (VID and PID) and the name strings. The HID report descriptor gives the format of the messages (reports) the device will send. Here it is a standard keyboard: one byte for the modifier keys such as Shift, and room for six keys pressed at once. TinyUSB calls each `..._cb` function when the computer asks for that descriptor.

```c
#include "tusb.h"
#include <string.h>

/* HID Report Descriptor: standard keyboard */
static const uint8_t desc_hid_report[] = {
    TUD_HID_REPORT_DESC_KEYBOARD()
};

/* Device Descriptor */
static const tusb_desc_device_t desc_device = {
    .bLength            = sizeof(tusb_desc_device_t),
    .bDescriptorType    = TUSB_DESC_DEVICE,
    .bcdUSB             = 0x0200,
    .bDeviceClass       = 0x00,
    .bDeviceSubClass    = 0x00,
    .bDeviceProtocol    = 0x00,
    .bMaxPacketSize0    = CFG_TUD_ENDPOINT0_SIZE,
    .idVendor           = 0xCafe,
    .idProduct          = 0x4001,
    .bcdDevice          = 0x0100,
    .iManufacturer      = 1,
    .iProduct           = 2,
    .iSerialNumber      = 3,
    .bNumConfigurations = 1
};

const uint8_t *tud_descriptor_device_cb(void)
{
    return (const uint8_t *)&desc_device;
}

/* Configuration Descriptor */
#define CONFIG_TOTAL_LEN (TUD_CONFIG_DESC_LEN + TUD_HID_DESC_LEN)

static const uint8_t desc_configuration[] = {
    TUD_CONFIG_DESCRIPTOR(1, 1, 0, CONFIG_TOTAL_LEN,
                          TUSB_DESC_CONFIG_ATT_REMOTE_WAKEUP, 100),
    TUD_HID_DESCRIPTOR(0, 0, HID_ITF_PROTOCOL_KEYBOARD,
                       sizeof(desc_hid_report), 0x81, CFG_TUD_HID_EP_BUFSIZE, 10)
};

const uint8_t *tud_descriptor_configuration_cb(uint8_t index)
{
    (void)index;
    return desc_configuration;
}

/* HID Report Descriptor callback */
const uint8_t *tud_hid_descriptor_report_cb(uint8_t instance)
{
    (void)instance;
    return desc_hid_report;
}

/* String Descriptors */
static const char *string_desc_arr[] = {
    [0] = (const char[]){0x09, 0x04},   /* Language: English (US) */
    [1] = "SiliconWit",                  /* Manufacturer */
    [2] = "Pico Text Injector",          /* Product */
    [3] = "000001"                       /* Serial */
};

static uint16_t _desc_str[32];

const uint16_t *tud_descriptor_string_cb(uint8_t index, uint16_t langid)
{
    (void)langid;
    uint8_t chr_count;

    if (index == 0) {
        memcpy(&_desc_str[1], string_desc_arr[0], 2);
        chr_count = 1;
    } else {
        if (index >= sizeof(string_desc_arr) / sizeof(string_desc_arr[0]))
            return NULL;
        const char *str = string_desc_arr[index];
        chr_count = strlen(str);
        if (chr_count > 31) chr_count = 31;
        for (uint8_t i = 0; i < chr_count; i++)
            _desc_str[1 + i] = str[i];
    }

    _desc_str[0] = (TUSB_DESC_STRING << 8) | (2 * chr_count + 2);
    return _desc_str;
}
```

## Complete Firmware

<InArticleAd />


A USB keyboard does not send letters. It sends reports of which keys are down now, each key named by a number, its keycode. To type one character the firmware sends a report with that keycode (key down), then an empty report (key up). It waits for enumeration and one more second for the computer to load its driver, then types the message.

```c
#include <stdlib.h>
#include <stdio.h>
#include <string.h>

#include "pico/stdlib.h"
#include "bsp/board.h"
#include "tusb.h"

/* Message to type when plugged in */
static const char *MESSAGE = "Hello from Raspberry Pi Pico!\n";

/* Convert an ASCII character to HID keycode and modifier */
static void char_to_keycode(char c, uint8_t *keycode, uint8_t *modifier)
{
    *modifier = 0;
    *keycode  = 0;

    if (c >= 'a' && c <= 'z') {
        *keycode = HID_KEY_A + (c - 'a');
    } else if (c >= 'A' && c <= 'Z') {
        *keycode  = HID_KEY_A + (c - 'A');
        *modifier = KEYBOARD_MODIFIER_LEFTSHIFT;
    } else if (c >= '1' && c <= '9') {
        *keycode = HID_KEY_1 + (c - '1');
    } else if (c == '0') {
        *keycode = HID_KEY_0;
    } else {
        switch (c) {
            case ' ':  *keycode = HID_KEY_SPACE;          break;
            case '\n': *keycode = HID_KEY_ENTER;          break;
            case '\t': *keycode = HID_KEY_TAB;            break;
            case '.':  *keycode = HID_KEY_PERIOD;         break;
            case ',':  *keycode = HID_KEY_COMMA;          break;
            case '!':  *keycode = HID_KEY_1;
                       *modifier = KEYBOARD_MODIFIER_LEFTSHIFT; break;
            case '?':  *keycode = HID_KEY_SLASH;
                       *modifier = KEYBOARD_MODIFIER_LEFTSHIFT; break;
            case '-':  *keycode = HID_KEY_MINUS;          break;
            case '=':  *keycode = HID_KEY_EQUAL;          break;
            case '/':  *keycode = HID_KEY_SLASH;          break;
            case ':':  *keycode = HID_KEY_SEMICOLON;
                       *modifier = KEYBOARD_MODIFIER_LEFTSHIFT; break;
            case ';':  *keycode = HID_KEY_SEMICOLON;      break;
            case '\'': *keycode = HID_KEY_APOSTROPHE;     break;
            default:   *keycode = 0;                      break;
        }
    }
}

/* Wait while still servicing the USB stack. A plain sleep_ms() here would
   stop tud_task(), and TinyUSB would refuse the next report as "busy". */
static void usb_delay_ms(uint32_t ms)
{
    absolute_time_t end = make_timeout_time_ms(ms);
    while (!time_reached(end)) {
        tud_task();
    }
}

/* Send a single keystroke (press + release) */
static void send_key(uint8_t keycode, uint8_t modifier)
{
    uint8_t report[6] = {0};
    report[0] = keycode;

    /* Key press */
    tud_hid_keyboard_report(0, modifier, report);
    usb_delay_ms(15);

    /* Key release (empty report) */
    tud_hid_keyboard_report(0, 0, NULL);
    usb_delay_ms(15);
}

/* Type a full string character by character */
static void type_string(const char *str)
{
    for (size_t i = 0; i < strlen(str); i++) {
        uint8_t keycode, modifier;
        char_to_keycode(str[i], &keycode, &modifier);
        if (keycode != 0) {
            send_key(keycode, modifier);
            usb_delay_ms(50);  /* Delay between characters for readability */
        }
    }
}

/* TinyUSB HID callbacks (required by the stack) */
uint16_t tud_hid_get_report_cb(uint8_t instance, uint8_t report_id,
                                hid_report_type_t report_type,
                                uint8_t *buffer, uint16_t reqlen)
{
    (void)instance; (void)report_id; (void)report_type;
    (void)buffer;   (void)reqlen;
    return 0;
}

void tud_hid_set_report_cb(uint8_t instance, uint8_t report_id,
                            hid_report_type_t report_type,
                            const uint8_t *buffer, uint16_t bufsize)
{
    (void)instance; (void)report_id; (void)report_type;
    (void)buffer;   (void)bufsize;
}

int main(void)
{
    /* Initialize board and USB */
    board_init();
    tusb_init();

    /* Wait for USB to enumerate */
    while (!tud_mounted()) {
        tud_task();
        sleep_ms(10);
    }

    /* Give the host OS time to load the HID driver */
    usb_delay_ms(1000);

    /* Type the message */
    type_string(MESSAGE);

    /* Keep USB alive (required by TinyUSB) */
    while (1) {
        tud_task();
        sleep_ms(100);
    }

    return 0;
}
```

### How It Works

1. `board_init()` configures the Pico's clocks, GPIO, and on-board LED.
2. `tusb_init()` starts TinyUSB, and enumeration begins.
3. The loop calls `tud_task()` until `tud_mounted()` returns true: the computer has accepted the keyboard. `tud_task()` is the function in which TinyUSB does all its work, so the program must call it again and again.
4. After one second, `type_string()` takes each character of the message. `char_to_keycode()` finds its keycode (and Shift if needed), and `send_key()` sends the key-down report and then the key-up report.
5. After the message, the firmware keeps calling `tud_task()`, so the computer does not report the keyboard as removed.

One character takes 15 ms down, 15 ms up and a 50 ms pause: 80 ms, or 12.5 characters per second. The waits use `usb_delay_ms()`, which keeps calling `tud_task()`. With a plain `sleep_ms()` TinyUSB would not run between reports and would refuse the next report as busy, so the key-up report would never be sent. With much shorter waits, some operating systems lose keys.

## Building and Flashing

<InArticleAd />


<Steps>
1. Create the build directory and run CMake:
   ```bash
   cd usb-text-injector
   mkdir build && cd build
   cmake ..
   ```

2. Compile the project:
   ```bash
   make -j$(nproc)
   ```
   This produces `usb_text_injector.uf2` in the build directory. The output also shows flash and RAM usage.

3. Put the Pico into BOOTSEL mode: unplug it, hold the BOOTSEL button, plug it back in, then release the button.

4. Copy the UF2 file to the Pico:
   ```bash
   # Linux
   cp usb_text_injector.uf2 /media/$USER/RPI-RP2/

   # macOS
   cp usb_text_injector.uf2 /Volumes/RPI-RP2/

   # Windows (adjust drive letter)
   copy usb_text_injector.uf2 E:\
   ```

5. The Pico reboots, enumerates as a keyboard, waits one second, and types the message into whatever application has focus.
</Steps>

:::caution
Open a text editor and click into it before plugging the Pico in. The device will start typing into whatever window has focus. If that happens to be a terminal, it could execute unintended commands.
:::

## Exercises

<InArticleAd />


1. Modify the `MESSAGE` string to type your full name, email address, and a greeting on separate lines. Verify that special characters (periods, at-signs, colons) are handled correctly, and add any missing keycode mappings.
2. Add an on-board LED blink after each character is typed. Use `gpio_put(PICO_DEFAULT_LED_PIN, 1)` and `gpio_put(PICO_DEFAULT_LED_PIN, 0)` with a short delay. This gives visual feedback during typing.
3. Make the Pico wait for a button press before typing. Connect a tactile button between GP14 and GND, enable the internal pull-up with `gpio_pull_up()`, and only call `type_string()` when the button is pressed. This prevents accidental typing on every plug-in.
4. Extend the firmware to type the message repeatedly with a 5-second pause between cycles. Add a cycle counter and stop after 3 repetitions, then turn on the LED to indicate completion.

## Summary

<InArticleAd />


The RP2040 has two cores that share 264 KB of SRAM in six banks, joined by a bus fabric that lets them work at the same time. It starts from a ROM that no program can change, which is why a Pico can always be loaded again through BOOTSEL. CMake plans the build from `CMakeLists.txt`, and the result is a UF2 file that you copy to the Pico. A USB device tells the computer what it is with descriptors, and a keyboard types by sending key-down and key-up reports. Every project in this course uses the same SDK setup, CMake file and UF2 loading.
