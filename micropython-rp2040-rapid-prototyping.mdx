## What Is MicroPython?

<InArticleAd />


A C program is translated on your PC into instructions for the processor, and only those go to the board, like a book translated before it is sold. MicroPython works the other way round, like a live interpreter: a program that understands Python, the interpreter, is flashed to the board once, and after that you send it Python text. It is a small Python 3 for microcontrollers; with its compiler and part of the standard library it needs about 256 KB of flash and can run in 16 KB of RAM.

The RP2040 version has two hardware modules: `machine`, with classes for `Pin`, `PWM`, `ADC`, `I2C`, `SPI` and `Timer`, and `rp2`, which gives PIO through the `StateMachine` class and the `@rp2.asm_pio` decorator. Both reach the same hardware registers as the C SDK.

You trade running speed for working speed: a MicroPython loop that reads an ADC and sets a PWM duty cycle runs roughly 10 to 100 times slower than the same loop in C. For a display of sensor readings, a settings menu, a test rig or a first trial of a protocol this does not matter, and the development time you save is worth more.

### How It Works Internally

The slowness has a clear cause: between your text and the hardware there are more steps than in C.

```text
 ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ main.py  ├──>│ compiler ├──>│ bytecode │
 │ (text)   │   │ on Pico  │   │ in RAM   │
 └──────────┘   └──────────┘   └────┬─────┘
                                    v
 ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ RP2040   │<──┤ C        │<──┤ virtual  │
 │ hardware │   │ drivers  │   │ machine  │
 └──────────┘   └──────────┘   └──────────┘
```

<Steps>
1. You write a `.py` file, or type a line into the REPL.
2. The MicroPython compiler, which runs on the RP2040 itself, turns the text into bytecode: short instructions that are not processor instructions.
3. The virtual machine (VM), a loop written in C, reads each bytecode instruction and does what it says. This reading is the extra work that makes Python slow.
4. When you use `machine.Pin`, `machine.ADC` and so on, the VM calls drivers written in C, which use the same RP2040 registers as the Pico SDK.
</Steps>

The compiler runs on the microcontroller, not on your PC: this is why MicroPython needs more flash and RAM than a C program, and why you have no toolchain to install.

The REPL reads the line you type, runs it on the RP2040, prints the result, and waits for the next line. Try these lines to confirm that Python reaches the hardware:

## The `machine` Module

<InArticleAd />


The `machine` module is how MicroPython reaches the RP2040 hardware. Each peripheral you set up with the C SDK has a Python class here.

### Pin

The `Pin` class sets up a GPIO pin and reads or writes it.

```python
from machine import Pin

# Output: configure GP15 as a push-pull output
led = Pin(15, Pin.OUT)
led.value(1)  # Drive high
led.value(0)  # Drive low
led.toggle()  # Flip state

# Input: configure GP14 with internal pull-up
button = Pin(14, Pin.IN, Pin.PULL_UP)
state = button.value()  # Returns 0 or 1
```

Compare this with the C SDK equivalent:

```c
/* C SDK: configure GP15 as output, drive high */
gpio_init(15);
gpio_set_dir(15, GPIO_OUT);
gpio_put(15, 1);

/* C SDK: configure GP14 as input with pull-up */
gpio_init(14);
gpio_set_dir(14, GPIO_IN);
gpio_pull_up(14);
bool state = gpio_get(14);
```

The Python version is shorter because one `Pin(...)` call does the initialization, the direction and the pull-up, where C needs a call for each.

### PWM

The `PWM` class sets up a PWM output on a GPIO pin.

```python
from machine import Pin, PWM

pwm = PWM(Pin(15))       # Create PWM on GP15
pwm.freq(1000)           # Set frequency to 1 kHz
pwm.duty_u16(32768)      # 50% duty cycle (range: 0 to 65535)
pwm.duty_u16(0)          # Turn off
pwm.deinit()             # Release the PWM hardware
```

In MicroPython the duty cycle is always a 16-bit value, 0 always off and 65535 always on, whatever the PWM frequency: MicroPython works out the wrap value and the level for you. In C you choose the wrap value and write the level yourself.

### ADC

The `ADC` class reads from the RP2040's 12-bit analog-to-digital converter.

```python
from machine import ADC

pot = ADC(26)              # ADC on GP26 (channel 0)
raw = pot.read_u16()       # Returns 0 to 65535 (scaled from 12-bit)

# On-chip temperature sensor
temp_sensor = ADC(4)       # ADC channel 4 = internal temp sensor
raw_temp = temp_sensor.read_u16()
```

:::note
`read_u16()` returns a 16-bit value (0 to 65535), although the RP2040 ADC has 12 bits: MicroPython stretches the reading to 16 bits so that the same code works on boards with other converters, and it is no more exact for it. To get the 12-bit value back, shift right by 4: `raw_12bit = raw >> 4`. To get the voltage: `voltage = raw * 3.3 / 65535`. A reading of 32768 is 1.65 V.
:::

## Rebuilding the LED Controller

<InArticleAd />


The circuit is the one from [GPIO, PWM, and analog I/O](/education/embedded-programming-rpi-pico/gpio-pwm-analog-io/): the middle pin of the potentiometer on GP26, and the LED with its 220 ohm resistor on GP15. Only the program changes.

### Complete MicroPython Script

The script does two things in a loop: it copies the potentiometer reading to the PWM duty cycle, and it reads the temperature sensor inside the chip. One temperature reading moves by a degree or more from noise, so the script prints the average of the last 10 readings, a moving average, next to the single reading.

Create a file called `main.py` on the Pico's filesystem. MicroPython runs `main.py` by itself each time it starts.

```python title="main.py"
from machine import Pin, PWM, ADC
import time

# Hardware setup
pot = ADC(26)                  # Potentiometer on GP26 (ADC channel 0)
temp_sensor = ADC(4)           # On-chip temperature sensor (ADC channel 4)
led_pwm = PWM(Pin(15))        # LED on GP15
led_pwm.freq(1000)            # 1 kHz PWM frequency

# Moving average filter for temperature
FILTER_SIZE = 10
temp_buffer = [0.0] * FILTER_SIZE
temp_index = 0

def adc_to_voltage(raw_u16):
    """Convert a 16-bit ADC reading to voltage (0.0 to 3.3V)."""
    return raw_u16 * 3.3 / 65535

def read_temperature():
    """Read the on-chip temperature sensor and return degrees C."""
    raw = temp_sensor.read_u16()
    voltage = adc_to_voltage(raw)
    # RP2040 datasheet formula: T = 27 - (V - 0.706) / 0.001721
    return 27.0 - (voltage - 0.706) / 0.001721

def update_temp_filter(new_sample):
    """Add a sample to the moving average buffer and return the average."""
    global temp_index
    temp_buffer[temp_index] = new_sample
    temp_index = (temp_index + 1) % FILTER_SIZE
    return sum(temp_buffer) / FILTER_SIZE

def main():
    print("MicroPython LED Brightness Controller")
    print("ADC -> PWM with temperature monitoring")
    print("Press Ctrl+C to stop\n")

    # Pre-fill the temperature buffer
    for i in range(FILTER_SIZE):
        temp_buffer[i] = read_temperature()

    iteration = 0

    while True:
        # Read potentiometer
        pot_raw = pot.read_u16()
        pot_voltage = adc_to_voltage(pot_raw)

        # Map ADC reading directly to PWM duty cycle
        # Both are 16-bit (0 to 65535), so no scaling needed
        led_pwm.duty_u16(pot_raw)

        # Calculate duty cycle percentage
        duty_pct = pot_raw * 100.0 / 65535

        # Read and filter temperature
        temp_raw = read_temperature()
        temp_avg = update_temp_filter(temp_raw)

        # Formatted REPL output every 200ms (every 4th iteration at 50ms rate)
        if iteration % 4 == 0:
            print("ADC: {:5d} | {:.3f} V | Duty: {:5.1f}% | Temp: {:.1f} C (avg {:.1f} C)".format(
                pot_raw, pot_voltage, duty_pct, temp_raw, temp_avg))

        iteration += 1
        time.sleep_ms(50)

# Run the main loop
main()
```

### How It Maps to the C Version

The structure is the same as in the C firmware. Operation by operation:

| Operation | C SDK | MicroPython |
|-----------|-------|-------------|
| Initialize ADC | `adc_init(); adc_gpio_init(26);` | `pot = ADC(26)` |
| Read ADC | `adc_select_input(0); adc_read();` | `pot.read_u16()` |
| Configure PWM | 5 lines (function, divider, wrap, level, enable) | `PWM(Pin(15)); pwm.freq(1000)` |
| Set duty cycle | `pwm_set_chan_level(slice, chan, level)` | `led_pwm.duty_u16(value)` |
| Temperature formula | Same formula, manual `float` math | Same formula, Python `float` |
| Print output | `printf(...)` | `print("...".format(...))` |
| Delay | `sleep_ms(200)` | `time.sleep_ms(50)` |

The C version has about 90 lines and the MicroPython version about 70. The larger difference is in how you work. In MicroPython you can change the filter size, the print format or add a sensor, and see the result in seconds, with no build and no flash:

```text
 ┌──────────────────┐  ┌──────────────────┐
 │  C SDK           │  │  MicroPython     │
 │                  │  │                  │
 │  Edit main.c     │  │  Edit main.py    │
 │       │          │  │       │          │
 │  cmake + make    │  │  Copy to Pico    │
 │  (about 30 s)    │  │  (about 1 s)     │
 │       │          │  │       │          │
 │  Flash the UF2   │  │  Ctrl+D restart  │
 │  (about 5 s)     │  │  (under 1 s)     │
 │       │          │  │       │          │
 │  Test            │  │  Test            │
 │                  │  │                  │
 │  Cycle: ~40 s    │  │  Cycle: ~3 s     │
 └──────────────────┘  └──────────────────┘
```

## PIO in MicroPython

<InArticleAd />


Python is too slow and too uneven to make a signal with microsecond timing, and it does not need to: the PIO state machines are hardware and keep exact time once started, whichever language started them. In [PIO state machines](/education/embedded-programming-rpi-pico/pio-programmable-io-state-machines/) you wrote a WS2812B driver as a `.pio` file built with the SDK; in MicroPython you write the same PIO program inside a Python file.

### PIO Assembly in Python

A decorator is a line that begins with `@`, placed above a function, that changes what the function is. `@rp2.asm_pio` turns a Python function into a PIO program: each call inside the function becomes one PIO instruction, the same 16-bit instruction word that the `.pio` file produces.

Here is the WS2812B driver in MicroPython:

```python title="ws2812b_pio.py"
import rp2
from machine import Pin
import time

@rp2.asm_pio(sideset_init=rp2.PIO.OUT_LOW, out_shiftdir=rp2.PIO.SHIFT_LEFT,
             autopull=True, pull_thresh=24)
def ws2812():
    T1 = 2
    T2 = 5
    T3 = 3
    wrap_target()
    label("bitloop")
    out(x, 1)               .side(0) [T3 - 1]   # Shift 1 bit, pin low, delay T3-1
    jmp(not_x, "do_zero")   .side(1) [T1 - 1]   # If 0, jump. Pin high, delay T1-1
    jmp("bitloop")           .side(1) [T2 - 1]   # Bit=1: stay high T2 more, loop
    label("do_zero")
    nop()                    .side(0) [T2 - 1]   # Bit=0: pin low for T2
    wrap()

# Create a state machine on PIO0, state machine 0, at 8 MHz, on GP2
sm = rp2.StateMachine(0, ws2812, freq=8_000_000, sideset_base=Pin(2))
sm.active(1)

NUM_PIXELS = 8

def put_pixel(grb):
    """Send a 24-bit GRB value to the state machine."""
    sm.put(grb, 8)  # Second argument: shift left by 8 so the 24 bits sit at the top

def wheel(pos):
    """Color wheel: input 0-255, output (g, r, b) packed as GRB integer."""
    if pos < 85:
        return (pos * 3) << 16 | (255 - pos * 3) << 8 | 0
    elif pos < 170:
        pos -= 85
        return (255 - pos * 3) << 16 | 0 << 8 | (pos * 3)
    else:
        pos -= 170
        return 0 << 16 | (pos * 3) << 8 | (255 - pos * 3)

# Rainbow chase animation
t = 0
while True:
    for i in range(NUM_PIXELS):
        hue = (t * 3 + i * 32) & 0xFF
        put_pixel(wheel(hue))
    time.sleep_ms(50)
    t += 1
```

### Mapping .pio Syntax to Python Decorator Syntax

Each element of the `.pio` file has a matching form in Python:

| `.pio` File Syntax | MicroPython Decorator Syntax |
|---------------------|------------------------------|
| `.side_set 1` | `sideset_init=rp2.PIO.OUT_LOW` |
| `.wrap_target` | `wrap_target()` (called inside the function) |
| `.wrap` | `wrap()` (called inside the function) |
| `out x, 1 side 0 [2]` | `out(x, 1) .side(0) [2]` |
| `jmp !x do_zero side 1 [1]` | `jmp(not_x, "do_zero") .side(1) [1]` |
| `nop side 0 [4]` | `nop() .side(0) [4]` |
| `.define public T1 2` | `T1 = 2` (regular Python variable) |
| Autopull config in C init code | `autopull=True, pull_thresh=24` in decorator |

The decorator parameters (`sideset_init`, `out_shiftdir`, `autopull`, `pull_thresh`) replace the settings that C makes with `sm_config_set_sideset_pins()`, `sm_config_set_out_shift()` and similar functions.

The call `rp2.StateMachine()` replaces the C initialization: it takes a state machine, loads the program, sets the clock divider from the `freq` parameter, and assigns the pins.

## C vs Python: Side-by-Side Comparison

<InArticleAd />


"Slower" is not a number you can design with. This test gives one: how many ADC samples can each language read in one second?

### MicroPython Benchmark

```python title="benchmark_mp.py"
from machine import ADC
import time

adc = ADC(26)

start = time.ticks_us()
count = 0
while count < 10000:
    adc.read_u16()
    count += 1
elapsed = time.ticks_diff(time.ticks_us(), start)

samples_per_sec = count * 1_000_000 // elapsed
print("MicroPython: {} samples in {} us".format(count, elapsed))
print("Rate: {} samples/sec".format(samples_per_sec))
```

### C SDK Benchmark

```c title="benchmark.c"
#include <stdio.h>
#include "pico/stdlib.h"
#include "hardware/adc.h"
#include "hardware/timer.h"

int main(void) {
    stdio_init_all();
    adc_init();
    adc_gpio_init(26);
    adc_select_input(0);

    sleep_ms(2000);

    uint64_t start = time_us_64();
    for (int i = 0; i < 100000; i++) {
        adc_read();
    }
    uint64_t elapsed = time_us_64() - start;

    uint32_t rate = (uint64_t)100000 * 1000000 / elapsed;
    printf("C SDK: 100000 samples in %llu us\n", elapsed);
    printf("Rate: %lu samples/sec\n", rate);

    while (1) tight_loop_contents();
    return 0;
}
```

### Results Comparison

| Metric | C SDK | MicroPython | Ratio |
|--------|-------|-------------|-------|
| Lines of code (full project) | ~90 | ~70 | 1.3x fewer in Python |
| Build time | ~30 seconds (cmake + make) | 0 (no build step) | Instant |
| Flash usage | ~40 KB (.uf2) | ~650 KB (firmware) + ~2 KB (script) | 16x more |
| RAM usage | ~8 KB | ~60 KB (interpreter + heap) | 7.5x more |
| ADC loop speed | ~480,000 samples/sec | ~18,000 samples/sec | ~27x faster in C |
| Development time (this project) | ~30 minutes | ~10 minutes | 3x faster in Python |

Read the ADC row as times: in C one reading takes about 2 microseconds, the speed of the converter itself; in MicroPython about 56 microseconds, nearly all of it the virtual machine at work. Your own board will give somewhat different numbers.

Speed is one limit; evenness is the other. MicroPython stops now and then to free memory that is no longer used (garbage collection), and such a stop can last a few milliseconds, so a Python loop cannot promise that every pass comes on time.

## Writing a C Extension Module

<InArticleAd />


Often one small function needs the speed and the rest of the program does not. Write that function in C and build it into the MicroPython firmware; Python then calls it by name, as it calls `machine.ADC`.

### Module Structure Overview

A C extension module has three parts: the C function, a table that gives the function its Python name, and a macro that registers the module. This small example reads the ADC many times in C and returns the average.

```c title="modfastadc.c"
#include "py/runtime.h"
#include "py/obj.h"
#include "hardware/adc.h"

/* C implementation: read N ADC samples and return the average */
static mp_obj_t fastadc_average(mp_obj_t n_obj) {
    int n = mp_obj_get_int(n_obj);
    if (n <= 0 || n > 10000) {
        mp_raise_ValueError(MP_ERROR_TEXT("n must be 1 to 10000"));
    }

    uint32_t total = 0;
    for (int i = 0; i < n; i++) {
        total += adc_read();
    }
    return mp_obj_new_int(total / n);
}
static MP_DEFINE_CONST_FUN_OBJ_1(fastadc_average_obj, fastadc_average);

/* Module globals table */
static const mp_rom_map_elem_t fastadc_module_globals_table[] = {
    { MP_ROM_QSTR(MP_QSTR___name__), MP_ROM_QSTR(MP_QSTR_fastadc) },
    { MP_ROM_QSTR(MP_QSTR_average), MP_ROM_PTR(&fastadc_average_obj) },
};
static MP_DEFINE_CONST_DICT(fastadc_module_globals, fastadc_module_globals_table);

/* Module definition */
const mp_obj_module_t fastadc_module = {
    .base = { &mp_type_module },
    .globals = (mp_obj_dict_t *)&fastadc_module_globals,
};

/* Register the module so "import fastadc" works */
MP_REGISTER_MODULE(MP_QSTR_fastadc, fastadc_module);
```

### Building Custom Firmware

To compile this into MicroPython, you clone the MicroPython repository, place your module source in the `ports/rp2/` directory (or use the `USER_C_MODULES` mechanism), and rebuild:

```bash
git clone https://github.com/micropython/micropython.git
cd micropython
make -C mpy-cross                      # Build the cross-compiler first
cd ports/rp2
make submodules                         # Fetch required submodules
make USER_C_MODULES=path/to/your/modules/micropython.cmake
```

The build produces a new `.uf2` file that includes your C module. Flash it to the Pico using the same BOOTSEL procedure, and your module becomes importable:

```python
>>> import fastadc
>>> from machine import ADC
>>> adc = ADC(26)
>>> avg = fastadc.average(1000)   # 1000 samples averaged in C, returned to Python
>>> print(avg)
```

Use this for fast sampling loops and signal processing. For most program logic, plain MicroPython is fast enough.

```bash
mpremote connect auto run benchmark_mp.py

# Remove a file from the Pico
mpremote connect auto rm :old_script.py

# Hard reset the Pico (use soft-reset for a soft reset)
mpremote connect auto reset
```

You can join commands with `+`:

```bash
# Upload, reset, and connect to REPL in one command
mpremote connect auto cp main.py :main.py + reset + repl
```

### Filesystem Layout

A typical MicroPython project on the Pico looks like this:

<FileTree>
- boot.py
- main.py
- lib/
  - ws2812b_pio.py
  - sensor_utils.py
</FileTree>

`boot.py` runs first at every start and is for low-level settings such as the CPU frequency. `main.py` runs directly after it and holds your program. MicroPython looks in `lib/` when you import, so any `.py` file there can be imported by name.

## When to Use MicroPython vs C

<InArticleAd />


You need not choose one language for a whole project. Many projects begin in MicroPython and move a part to C only when a measurement shows the need; others never need the speed and stay in MicroPython for good.

### Decision Framework

| Factor | Favor MicroPython | Favor C SDK |
|--------|-------------------|-------------|
| Timing | Being a few milliseconds late does no harm | Microsecond timing, or a deadline that must always hold |
| How often the code changes | Trials and frequent changes | Fixed requirements |
| Kind of work | Logic (parsers, state machines, menus) | Calculation (signal processing, motor control loops) |
| Flash and RAM | Room to spare (the Pico has 2 MB flash, 264 KB RAM) | Tight memory |
| The team | Knows Python, new to embedded work | Knows C and the SDK |
| Debugging | At the REPL, line by line | With `printf`, or a debug probe and GDB |
| Power | Not critical (powered from USB) | Battery, with long deep sleep |
| PIO programs | Same result (decorator) | Same result (`.pio` file) |

A control loop that keeps a machine inside safe limits belongs on the C side: it must not wait for a pause of the interpreter.

### Hybrid Approach

A C extension module lets you mix the two: the program in MicroPython, and in C only the functions that need it. This suits a project that is mostly settings, user interface or network communication, with a small fast sampling loop.

PIO programs give the same result from both languages, because the PIO hardware runs by itself once started: a WS2812B driver written with `@rp2.asm_pio` makes the same pulses as the `.pio` file built with the C SDK. Python is slower only in feeding it data.

## Summary

- MicroPython puts an interpreter on the board. You send it text, so a change takes seconds and needs no build.
- The price is speed, memory and evenness: about 27 times slower on the ADC loop, about 650 KB of flash, and short pauses for garbage collection.
- The `machine` and `rp2` modules reach the same hardware as the C SDK.
- Exact timing comes from hardware, not from the language: a PIO program makes the same pulses when Python starts it.
- Measure first. Then move only the slow function to a C extension module.
