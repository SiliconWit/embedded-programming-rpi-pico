A device that needs its own driver is one many people cannot use: someone must write the driver for each operating system, the user must install it, and an update can break it. USB avoids this with device classes: a device that describes itself in a standard way works with the driver every computer already has. ## USB Device Architecture

<InArticleAd />


When you plug in a USB device, the computer (USB calls it the host) knows nothing about it and cannot guess whether it is a mouse, a printer or a gamepad. So it asks, and the device answers with descriptors: small blocks of bytes in a fixed format that state what the device is and how to talk to it. From the answers the host chooses a driver. This exchange at plug-in is called enumeration.

### Descriptor Hierarchy

The descriptors answer four questions, each one inside the one before:

| Level | Descriptor | The question it answers |
|-------|-----------|---------|
| 1 | Device | Who are you? Vendor ID (VID), product ID (PID), USB version |
| 2 | Configuration | Which functions do you offer together, and how much current do you need? |
| 3 | Interface | What is this one function, and which class does it belong to (HID, CDC, mass storage)? |
| 4 | Endpoint | Through which channel does its data flow? Direction, transfer type, packet size, how often |

An endpoint is a numbered channel inside the device. Directions are named from the side of the host: IN is device to host, OUT is host to device. For the gamepad of this lesson the answers are:

```text
 Device                  vendor and product ID
 └─ Configuration 1      100 mA
    ├─ Interface 0, 1    CDC: serial port
    │  ├─ Endpoint 1 IN  interrupt: status
    │  ├─ Endpoint 2 OUT bulk: from the PC
    │  └─ Endpoint 2 IN  bulk: to the PC
    └─ Interface 2       HID: the gamepad
       └─ Endpoint 3 IN  interrupt: 8 ms
```

Most devices have one configuration. The serial port takes two interfaces because the CDC class splits control and data.

### USB Transfer Types

A USB device never sends on its own. The host asks each endpoint in turn, and the device answers. Different data needs different treatment: a key press must arrive soon, a file must arrive complete, and sound must arrive on time even if a little is lost. So USB has four transfer types:

| Transfer Type | Guaranteed Bandwidth | Error Recovery | Use Case |
|--------------|---------------------|---------------|----------|
| Control | No | Yes | Device enumeration, setup requests |
| Interrupt | Yes (reserved slots) | Yes | HID reports (keyboards, mice, gamepads) |
| Bulk | No (uses leftover bandwidth) | Yes | Mass storage, CDC serial data |
| Isochronous | Yes | No | Audio streaming, video |

HID devices use interrupt transfers. The name misleads: the device does not interrupt the host; the host promises to ask the endpoint at a fixed interval, the `bInterval` field of the endpoint descriptor. The gamepad sets 8 ms, so the host asks 125 times a second, fast enough for a game. A block of data that a HID device sends is called a report.

### How TinyUSB Fits In

TinyUSB, the USB library included in the Pico SDK, does the protocol work: enumeration, answering descriptor requests, and the rules of each class. Your part is a set of callbacks: functions with fixed names that you write and TinyUSB calls when the host asks for something.

The callbacks you write are:

- `tud_descriptor_device_cb()`: returns the device descriptor
- `tud_descriptor_configuration_cb()`: returns the configuration descriptor (which includes all interface and endpoint descriptors)
- `tud_descriptor_string_cb()`: returns string descriptors (manufacturer, product, serial number)
- `tud_hid_descriptor_report_cb()`: returns the HID report descriptor
- `tud_hid_report_complete_cb()`: called after a report is sent, used to schedule the next one
- `tud_hid_set_report_cb()` and `tud_hid_get_report_cb()`: handle host requests for report data

Your main loop must call `tud_task()` again and again, because TinyUSB does its work inside that call. `tud_hid_report()` sends gamepad data, but it only places the report in the endpoint's buffer; the host collects it when it next asks, up to 8 ms later.

### HID Class Overview

The HID class covers devices that a person operates: keyboards, mice, joysticks, gamepads, knobs and sliders. Its strength is one extra descriptor, the HID report descriptor, which states what each bit and byte of a report means. The operating system reads it and builds the input handler itself, which is why a HID device needs no driver of its own.

## HID Report Descriptor

<InArticleAd />


The gamepad sends 3 bytes every 8 ms, which alone are only three numbers to the host. The report descriptor is their key: it says which bits are buttons, which bytes are axes, and what range each value has.

```text
 One report: 3 bytes

    byte 0         byte 1         byte 2
 ┌───────────┐  ┌───────────┐  ┌───────────┐
 │ 0000 YXBA │  │  X axis   │  │  Y axis   │
 └───────────┘  └───────────┘  └───────────┘
  4 unused bits  -127 to 127    -127 to 127
  4 button bits
```

### Report Descriptor Concepts

The descriptor is a list of items. Each item is a tag byte followed by its data. Most items do not describe data themselves. They set a value that stays in force, and an `Input` item then creates the fields with the values in force at that moment. There are three kinds of item:

- Global items stay in force until changed: `Usage Page`, `Logical Minimum`, `Logical Maximum`, `Report Size` (bits in one field), `Report Count` (number of fields).
- Local items apply only to the next main item: `Usage`, `Usage Minimum`, `Usage Maximum`. A usage is a number that names what a field is for, such as "X axis" or "Button 2". A usage page is the list the number is taken from.
- Main items create the fields or group them: `Input`, `Output`, `Feature`, `Collection`.

### Building the Gamepad Descriptor

Here is the descriptor for the 3-byte report, byte by byte:

```c
static const uint8_t desc_hid_report[] = {
    0x05, 0x01,        /* Usage Page (Generic Desktop)           */
    0x09, 0x05,        /* Usage (Game Pad)                       */
    0xA1, 0x01,        /* Collection (Application)               */

    /* --- Buttons --- */
    0x05, 0x09,        /*   Usage Page (Button)                  */
    0x19, 0x01,        /*   Usage Minimum (Button 1)             */
    0x29, 0x04,        /*   Usage Maximum (Button 4)             */
    0x15, 0x00,        /*   Logical Minimum (0)                  */
    0x25, 0x01,        /*   Logical Maximum (1)                  */
    0x95, 0x04,        /*   Report Count (4)                     */
    0x75, 0x01,        /*   Report Size (1 bit)                  */
    0x81, 0x02,        /*   Input (Data, Variable, Absolute)     */

    /* 4-bit padding to fill the rest of the byte */
    0x95, 0x01,        /*   Report Count (1)                     */
    0x75, 0x04,        /*   Report Size (4 bits)                 */
    0x81, 0x03,        /*   Input (Constant, Variable, Absolute) */

    /* --- Analog Axes --- */
    0x05, 0x01,        /*   Usage Page (Generic Desktop)         */
    0x09, 0x30,        /*   Usage (X)                            */
    0x09, 0x31,        /*   Usage (Y)                            */
    0x15, 0x81,        /*   Logical Minimum (-127)               */
    0x25, 0x7F,        /*   Logical Maximum (127)                */
    0x95, 0x02,        /*   Report Count (2)                     */
    0x75, 0x08,        /*   Report Size (8 bits)                 */
    0x81, 0x02,        /*   Input (Data, Variable, Absolute)     */

    0xC0               /* End Collection                         */
};
```

Read it from the top:

1. Usage Page (Generic Desktop) and Usage (Game Pad) say what the device is: usage 0x05 on page 0x01. The operating system then treats it as a game controller.
2. Collection (Application) groups everything up to End Collection into one device.
3. The buttons: Usage Page 0x09 (Button), with Usage Minimum 1 and Usage Maximum 4, names four buttons. Report Size 1 and Report Count 4 make four fields of 1 bit. The `Input` item creates them. Its flags 0x02 mean "Data, Variable, Absolute": each bit is the present state of one button.
4. The padding: a report must be a whole number of bytes, and the buttons use only 4 bits. One field of 4 bits with the flag Constant (0x03) fills the byte and tells the host to ignore it. Total so far: 1 byte.
5. The axes: back on Usage Page 0x01, two usages, X (0x30) and Y (0x31). Report Size 8 and Report Count 2 make two fields of 8 bits, each from -127 to 127. Total: $1 + 2 = 3$ bytes for each report.

### The Report Data Structure

The firmware must send exactly the bytes that the descriptor promises. In C this is a packed struct. The word packed tells the compiler to add no empty bytes between the members:

```c
typedef struct __attribute__((packed)) {
    uint8_t buttons;   /* Bits 0-3: buttons A,B,X,Y. Bits 4-7: padding */
    int8_t  x;         /* Joystick X axis: -127 to 127 */
    int8_t  y;         /* Joystick Y axis: -127 to 127 */
} gamepad_report_t;
```

## TinyUSB Configuration

<InArticleAd />


TinyUSB needs three things from you: a configuration header (`tusb_config.h`), a descriptors file (`usb_descriptors.c`), and the correct CMake setup.

### tusb_config.h

TinyUSB supports many classes, and each one costs memory. This header says which ones to build in:

```c
#ifndef TUSB_CONFIG_H
#define TUSB_CONFIG_H

#include "pico/stdlib.h"

/* Board and MCU selection (Pico SDK handles these) */
#define CFG_TUSB_MCU           OPT_MCU_RP2040
#define CFG_TUSB_OS            OPT_OS_PICO

/* USB device configuration: port 0 is a device. Without this
   line, tusb_init() does not build with SDK 2.x. */
#define CFG_TUSB_RHPORT0_MODE  OPT_MODE_DEVICE
#define CFG_TUD_ENABLED        1

/* Enable HID and CDC classes */
#define CFG_TUD_HID            1
#define CFG_TUD_CDC            1

/* Endpoint buffer sizes */
#define CFG_TUD_HID_EP_BUFSIZE 16
#define CFG_TUD_CDC_EP_BUFSIZE 64
#define CFG_TUD_CDC_RX_BUFSIZE 256
#define CFG_TUD_CDC_TX_BUFSIZE 256

#endif /* TUSB_CONFIG_H */
```

`CFG_TUD_HID` and `CFG_TUD_CDC` each set to 1 means one instance of each class. `CFG_TUD_HID_EP_BUFSIZE` must be at least as large as your largest HID report (3 bytes in our case, so 16 is plenty).

### usb_descriptors.c

This file, the longest in the project, holds every descriptor and the callbacks that hand them to TinyUSB. It follows the four levels above: device, configuration with its interfaces and endpoints, then the strings.

```c
#include "tusb.h"
#include "pico/unique_id.h"
#include <string.h>

/* ---------- Device Descriptor ---------- */

static const tusb_desc_device_t desc_device = {
    .bLength            = sizeof(tusb_desc_device_t),
    .bDescriptorType    = TUSB_DESC_DEVICE,
    .bcdUSB             = 0x0200,         /* USB 2.0 */
    .bDeviceClass       = 0x00,           /* Defined at interface level */
    .bDeviceSubClass    = 0x00,
    .bDeviceProtocol    = 0x00,
    .bMaxPacketSize0    = CFG_TUD_ENDPOINT0_SIZE,
    .idVendor           = 0xCafe,         /* Test vendor ID */
    .idProduct          = 0x4001,         /* Product ID */
    .bcdDevice          = 0x0100,         /* Device version 1.0 */
    .iManufacturer      = 1,              /* String index 1 */
    .iProduct           = 2,              /* String index 2 */

    .bNumConfigurations = 1,
};

const uint8_t *tud_descriptor_device_cb(void)
{
    return (const uint8_t *)&desc_device;
}

/* ---------- HID Report Descriptor ---------- */

static const uint8_t desc_hid_report[] = {
    0x05, 0x01,        /* Usage Page (Generic Desktop)           */
    0x09, 0x05,        /* Usage (Game Pad)                       */
    0xA1, 0x01,        /* Collection (Application)               */

    /* Buttons */
    0x05, 0x09,        /*   Usage Page (Button)                  */
    0x19, 0x01,        /*   Usage Minimum (Button 1)             */
    0x29, 0x04,        /*   Usage Maximum (Button 4)             */
    0x15, 0x00,        /*   Logical Minimum (0)                  */
    0x25, 0x01,        /*   Logical Maximum (1)                  */
    0x95, 0x04,        /*   Report Count (4)                     */
    0x75, 0x01,        /*   Report Size (1 bit)                  */
    0x81, 0x02,        /*   Input (Data, Variable, Absolute)     */

    /* 4-bit padding */
    0x95, 0x01,        /*   Report Count (1)                     */
    0x75, 0x04,        /*   Report Size (4 bits)                 */
    0x81, 0x03,        /*   Input (Constant)                     */

    /* Analog axes */
    0x05, 0x01,        /*   Usage Page (Generic Desktop)         */
    0x09, 0x30,        /*   Usage (X)                            */
    0x09, 0x31,        /*   Usage (Y)                            */
    0x15, 0x81,        /*   Logical Minimum (-127)               */
    0x25, 0x7F,        /*   Logical Maximum (127)                */
    0x95, 0x02,        /*   Report Count (2)                     */
    0x75, 0x08,        /*   Report Size (8 bits)                 */
    0x81, 0x02,        /*   Input (Data, Variable, Absolute)     */

    0xC0               /* End Collection                         */
};

const uint8_t *tud_hid_descriptor_report_cb(uint8_t instance)
{
    (void)instance;
    return desc_hid_report;
}

/* ---------- Configuration Descriptor ---------- */

/*
 * Interface numbering:
 *   0 = CDC Communication Interface
 *   1 = CDC Data Interface
 *   2 = HID Interface
 *
 * Endpoint numbering:
 *   EP 0x81 = CDC Notification (interrupt IN)
 *   EP 0x02 = CDC Data OUT (bulk)
 *   EP 0x82 = CDC Data IN (bulk)
 *   EP 0x83 = HID IN (interrupt)
 */

#define ITF_NUM_CDC       0
#define ITF_NUM_CDC_DATA  1
#define ITF_NUM_HID       2
#define ITF_NUM_TOTAL     3

#define EPNUM_CDC_NOTIF   0x81
#define EPNUM_CDC_OUT     0x02
#define EPNUM_CDC_IN      0x82
#define EPNUM_HID         0x83

#define CONFIG_TOTAL_LEN  (TUD_CONFIG_DESC_LEN + TUD_CDC_DESC_LEN + \
                           TUD_HID_DESC_LEN)

static const uint8_t desc_configuration[] = {
    /* Configuration descriptor */
    TUD_CONFIG_DESCRIPTOR(1, ITF_NUM_TOTAL, 0, CONFIG_TOTAL_LEN,
                          0x00, 100),

    /* CDC: Communication + Data interfaces */
    TUD_CDC_DESCRIPTOR(ITF_NUM_CDC, 4, EPNUM_CDC_NOTIF, 8,
                       EPNUM_CDC_OUT, EPNUM_CDC_IN, 64),

    /* HID: Gamepad interface */
    TUD_HID_DESCRIPTOR(ITF_NUM_HID, 5, HID_ITF_PROTOCOL_NONE,
                       sizeof(desc_hid_report), EPNUM_HID,
                       CFG_TUD_HID_EP_BUFSIZE, 8),
};

const uint8_t *tud_descriptor_configuration_cb(uint8_t index)
{
    (void)index;
    return desc_configuration;
}

/* ---------- String Descriptors ---------- */

/* Language ID (US English) */
static const char *string_desc_arr[] = {
    [0] = (const char[]){0x09, 0x04},  /* Supported language: English */
    [1] = "Pico Workshop",             /* Manufacturer */
    [2] = "Pico Gamepad",              /* Product */
    [3] = NULL,                        /* Serial (filled from flash ID) */
    [4] = "Pico Gamepad CDC",          /* CDC interface */
    [5] = "Pico Gamepad HID",          /* HID interface */
};

static uint16_t _desc_str[32 + 1];

const uint16_t *tud_descriptor_string_cb(uint8_t index, uint16_t langid)
{
    (void)langid;

    uint8_t chr_count;

    if (index == 0) {
        memcpy(&_desc_str[1], string_desc_arr[0], 2);
        chr_count = 1;
    } else if (index == 3) {
        /* Generate serial number from the Pico's unique flash ID */
        pico_unique_board_id_t id;
        pico_get_unique_board_id(&id);

        chr_count = 0;
        for (int i = 0; i < PICO_UNIQUE_BOARD_ID_SIZE_BYTES; i++) {
            const char hex[] = "0123456789ABCDEF";
            _desc_str[1 + chr_count++] = hex[(id.id[i] >> 4) & 0x0F];
            _desc_str[1 + chr_count++] = hex[id.id[i] & 0x0F];
        }
    } else {
        if (index >= sizeof(string_desc_arr) / sizeof(string_desc_arr[0])) {
            return NULL;
        }

        const char *str = string_desc_arr[index];
        chr_count = (uint8_t)strlen(str);
        if (chr_count > 31) chr_count = 31;

        for (uint8_t i = 0; i < chr_count; i++) {
            _desc_str[1 + i] = str[i];
        }
    }

    /* First word: length and descriptor type */
    _desc_str[0] = (uint16_t)((TUSB_DESC_STRING << 8) |
                               (2 * chr_count + 2));

    return _desc_str;
}
```

The parts, in the order of the file:

- Device descriptor. `bDeviceClass = 0x00` means "look at my interfaces to learn my class". A composite device must say this, because it has more than one class. The vendor ID 0xCafe is for tests only. A product that is sold needs a vendor ID from USB-IF, the body that publishes the USB standard. The fields `iManufacturer`, `iProduct` and `iSerialNumber` are index numbers into the string table.
- Configuration descriptor. The `TUD_CONFIG_DESCRIPTOR` macro writes the 9-byte header. The total length must count this header and every interface and endpoint descriptor after it, because the host reads exactly that many bytes. The last parameter (100) is the maximum current in mA.
- CDC descriptor. `TUD_CDC_DESCRIPTOR` writes the two interfaces of a serial port: one for control signals and one for the data. The notification endpoint is interrupt IN, and the data endpoints are bulk IN and OUT.
- HID descriptor. `TUD_HID_DESCRIPTOR` writes the HID interface with one interrupt IN endpoint. Its last parameter is the polling interval, 8 ms. `HID_ITF_PROTOCOL_NONE` says that this is not a simple keyboard or mouse of the kind a PC can use before its operating system starts. The host must read the report descriptor.
- String descriptors. USB text uses 16 bits for each character (UTF-16), so the callback widens each ASCII character. The serial number at index 3 comes from the unique 64-bit ID of the Pico's flash chip, so every board has its own.

## Gamepad Firmware

<InArticleAd />


With the descriptors in place, the main firmware reads the joystick and buttons, packs the data into a HID report, and sends it whenever TinyUSB is ready.

### Circuit Connections

A thumb joystick is two potentiometers. Each gives a voltage between 0 V and 3.3 V that follows the position of the stick on one axis.

```text
 ┌──────────────────┐    ┌──────────────┐
 │  Pico            │    │  Thumb       │
 │  GP26 (ADC0) ────┼────┤  VRx         │
 │  GP27 (ADC1) ────┼────┤  VRy         │
 │  3V3 ────────────┼────┤  VCC         │
 │  GND ────────────┼────┤  GND         │
 │                  │    └──────────────┘
 │  GP10 ─┤BTN A├── GND
 │  GP11 ─┤BTN B├── GND
 │  GP12 ─┤BTN X├── GND
 │  GP13 ─┤BTN Y├── GND
 │                  │
 │      USB ────────┼──── To PC
 └───────┤├─────────┘
```

Each button connects between the GPIO pin and GND. The firmware enables the internal pull-up resistors, so a pin reads high when released and low when pressed. Power the joystick from 3V3 and never from 5 V: an ADC pin must not see more than 3.3 V.

### main.c

```c
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

#include "pico/stdlib.h"
#include "bsp/board.h"
#include "hardware/adc.h"
#include "tusb.h"

/* ---------- Pin definitions ---------- */

#define JOY_X_PIN       26     /* ADC0 */
#define JOY_Y_PIN       27     /* ADC1 */
#define JOY_X_CHANNEL   0
#define JOY_Y_CHANNEL   1

#define BTN_A_PIN       10
#define BTN_B_PIN       11
#define BTN_X_PIN       12
#define BTN_Y_PIN       13

/* ---------- Joystick configuration ---------- */

#define ADC_CENTER      2048   /* 12-bit ADC midpoint */
#define DEAD_ZONE       100    /* Ignore values within this range of center */

/* Rest position of each axis, measured at power-up in main() */
static int32_t center_x = ADC_CENTER;
static int32_t center_y = ADC_CENTER;

/* ---------- Report structure (must match HID report descriptor) ---------- */

typedef struct __attribute__((packed)) {
    uint8_t buttons;   /* Bits 0-3: A, B, X, Y. Bits 4-7: padding (zero) */
    int8_t  x;         /* -127 to 127 */
    int8_t  y;         /* -127 to 127 */
} gamepad_report_t;

static gamepad_report_t last_report = {0, 0, 0};
static bool report_pending = false;

/* ---------- ADC helpers ---------- */

static void adc_setup(void)
{
    adc_init();
    adc_gpio_init(JOY_X_PIN);
    adc_gpio_init(JOY_Y_PIN);
}

static uint16_t adc_read_channel(uint8_t channel)
{
    adc_select_input(channel);
    return adc_read();
}

/* Convert 12-bit ADC (0-4095) to signed 8-bit (-127 to 127) with dead zone */
static int8_t adc_to_axis(uint16_t raw, int32_t center)
{
    int32_t centered = (int32_t)raw - center;

    /* Apply dead zone: if the joystick is near center, report zero */
    if (abs((int)centered) < DEAD_ZONE) {
        return 0;
    }

    /* Scale from [-2048, 2047] to [-127, 127] */
    int32_t scaled = (centered * 127) / 2048;

    /* Clamp */
    if (scaled > 127)  scaled = 127;
    if (scaled < -127) scaled = -127;

    return (int8_t)scaled;
}

/* ---------- Button helpers ---------- */

static const uint8_t btn_pins[] = {BTN_A_PIN, BTN_B_PIN, BTN_X_PIN, BTN_Y_PIN};

static void buttons_setup(void)
{
    for (int i = 0; i < 4; i++) {
        gpio_init(btn_pins[i]);
        gpio_set_dir(btn_pins[i], GPIO_IN);
        gpio_pull_up(btn_pins[i]);
    }
}

static uint8_t buttons_read(void)
{
    uint8_t result = 0;

    for (int i = 0; i < 4; i++) {
        /* Button pressed = pin LOW (active low with pull-up) */
        if (!gpio_get(btn_pins[i])) {
            result |= (1 << i);
        }
    }

    return result;
}

/* ---------- HID report helpers ---------- */

static void send_gamepad_report(void)
{
    gamepad_report_t report;

    report.buttons = buttons_read();
    report.x = adc_to_axis(adc_read_channel(JOY_X_CHANNEL), center_x);
    report.y = adc_to_axis(adc_read_channel(JOY_Y_CHANNEL), center_y);

    /* Only send if something changed, or periodically to keep alive */
    if (memcmp(&report, &last_report, sizeof(report)) != 0 || report_pending) {
        if (tud_hid_ready()) {
            tud_hid_report(0, &report, sizeof(report));
            last_report = report;
            report_pending = false;
        }
    }
}

/* ---------- TinyUSB HID callbacks ---------- */

/* Called when a report transfer completes. Schedule the next one. */
void tud_hid_report_complete_cb(uint8_t instance, uint8_t const *report,
                                 uint16_t len)
{
    (void)instance;
    (void)report;
    (void)len;

    /* Mark that we should send another report on the next cycle */
    report_pending = true;
}

/* Called when the host sends a SET_REPORT request (e.g., LED indicators).
   Our gamepad has no outputs, so we just acknowledge it. */
void tud_hid_set_report_cb(uint8_t instance, uint8_t report_id,
                            hid_report_type_t report_type,
                            uint8_t const *buffer, uint16_t bufsize)
{
    (void)instance;
    (void)report_id;
    (void)report_type;
    (void)buffer;
    (void)bufsize;
}

/* Called when the host sends a GET_REPORT request.
   Return the current gamepad state. */
uint16_t tud_hid_get_report_cb(uint8_t instance, uint8_t report_id,
                                hid_report_type_t report_type,
                                uint8_t *buffer, uint16_t reqlen)
{
    (void)instance;
    (void)report_id;
    (void)report_type;

    uint16_t copy_len = (reqlen < sizeof(last_report)) ? reqlen
                                                       : sizeof(last_report);
    memcpy(buffer, &last_report, copy_len);
    return copy_len;
}

/* ---------- CDC debug output ---------- */

static void cdc_debug_print(const gamepad_report_t *r)
{
    if (tud_cdc_connected()) {
        char buf[64];
        int len = snprintf(buf, sizeof(buf),
                           "BTN:0x%02X X:%4d Y:%4d\r\n",
                           r->buttons, r->x, r->y);
        tud_cdc_write(buf, (uint32_t)len);
        tud_cdc_write_flush();
    }
}

/* ---------- Main ---------- */

int main(void)
{
    /* Initialize the Pico board (sets up clocks, GPIO) */
    board_init();

    /* Initialize TinyUSB device stack */
    tusb_init();

    /* Initialize ADC for joystick */
    adc_setup();

    /* Nobody touches the stick while it is plugged in: take that
       position as the centre of each axis */
    center_x = adc_read_channel(JOY_X_CHANNEL);
    center_y = adc_read_channel(JOY_Y_CHANNEL);

    /* Initialize button GPIOs */
    buttons_setup();

    /* Track time for periodic debug output */
    uint32_t last_debug_ms = 0;

    while (1) {
        /* Let TinyUSB process USB events */
        tud_task();

        /* Send HID report if the device is mounted and ready */
        if (tud_mounted()) {
            send_gamepad_report();
        }

        /* Print debug info over CDC every 250 ms */
        uint32_t now = board_millis();
        if (now - last_debug_ms >= 250) {
            last_debug_ms = now;
            cdc_debug_print(&last_report);
        }
    }

    return 0;
}
```

### How the Firmware Works

Reading the stick. `adc_read_channel()` selects an input and makes one 12-bit conversion, 0 to 4095. The report needs a signed number from -127 to 127 with 0 at rest, so `adc_to_axis()` subtracts the centre, applies a dead zone, and scales: with the centre at 2048, a reading of 3072 gives $3072 - 2048 = 1024$, and $1024 \times 127 / 2048 = 63$, half of full travel.

The centre and the dead zone. A cheap thumb joystick often rests 100 to 200 counts away from the electrical midpoint 2048, and its reading moves a little by itself. With a fixed 2048 and a rest value of 1900, the gamepad would report -9 on that axis for ever, a slow drift in every game. So `main()` reads both axes once at power-up, when nobody touches the stick, and uses those readings as the centres. Every reading closer than 100 counts to the centre becomes 0: $100 / 2048$, about the inner 5% of the travel. The cost: an axis whose centre is far from 2048 reaches full travel on one side only (with the centre at 1900, the low side ends at -117).

Reading the buttons. A pressed button connects its pin to GND, so `gpio_get()` returns 0. `buttons_read()` inverts this and packs the four states into the lower 4 bits of one byte, as the report descriptor promises.

Sending the report. `send_gamepad_report()` reads all inputs and calls `tud_hid_report()` if the data changed or the previous report has gone. When the host has collected a report, TinyUSB calls `tud_hid_report_complete_cb()`, which sets `report_pending = true`, and the main loop prepares the next one. So the host receives a fresh report each time it asks.

Debug text. `cdc_debug_print()` writes the present report as text to the serial port every 250 ms, much slower than the HID reports. Open a serial terminal (PuTTY, minicom, or the Arduino serial monitor) to see the button and axis values.

## Adding CDC Debug Output

<InArticleAd />


The second function needs no extra hardware. You already set `CFG_TUD_CDC 1` in `tusb_config.h` and placed the CDC descriptor inside the configuration descriptor. When you plug in the device, the PC shows two things:

- A game controller (HID interface), in the game controller settings of the operating system
- A serial port (CDC interface): a COM port on Windows, /dev/ttyACM on Linux, or /dev/cu.usbmodem on macOS

Use the serial port while you develop: print raw ADC values to check the wiring, or count the reports sent. When the gamepad works, you can remove the debug output, or set `CFG_TUD_CDC` to 0 and remove the CDC descriptor.

### CDC Callbacks

The CDC callbacks are optional. Without them, TinyUSB accepts any baud rate and ignores the control signals. One is useful: a terminal program raises the DTR signal (data terminal ready) when it opens the port, and `tud_cdc_line_state_cb()` tells you so:

```c
void tud_cdc_line_state_cb(uint8_t itf, bool dtr, bool rts)
{
    (void)itf;
    (void)rts;

    if (dtr) {
        /* Terminal connected. Optionally reset state or print a banner. */
        tud_cdc_write_str("Pico Gamepad Debug Console\r\n");
        tud_cdc_write_flush();
    }
}
```

    ${CMAKE_CURRENT_LIST_DIR}
)

# Link against the Pico SDK and TinyUSB libraries
target_link_libraries(pico-gamepad
    pico_stdlib

)

What the libraries are for:

- `tinyusb_device` and `tinyusb_board` are TinyUSB. They come with the Pico SDK, so there is nothing to download.
- `pico_unique_id` gives `pico_get_unique_board_id()` for the USB serial number.
- `hardware_adc` gives the ADC functions for the joystick.
- `pico_enable_stdio_usb` is set to 0. The SDK's own USB serial port (the one `printf` used in earlier projects) brings its own descriptors, and a device can have only one set.

### Check it

- Released stick: the CDC line shows `X:   0 Y:   0`, and `jstest` shows 0 on both axes. Full travel shows about 127 on the CDC line; `jstest` shows about 32767, because Linux scales every axis to that range.
- Push the stick half-way: about 63 on the CDC line. Plug the Pico in while you hold the stick to one side, and that position becomes the centre: this is the limit of a centre measured at power-up.
- The serial number (`lsusb -v` on Linux, `system_profiler SPUSBDataType` on macOS) has 16 hex characters and is different on two Picos.

### Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| Device not recognized | Descriptor error | Check total length in configuration descriptor matches actual byte count |
| Axes stuck at zero | ADC wiring | Verify joystick VCC is connected to 3V3 and GND is connected |
| Axes jittery at center | Dead zone too small | Increase `DEAD_ZONE` from 100 to 200 |
| Buttons always pressed | Pull-up not enabled | Check that `gpio_pull_up()` is called, and buttons wire to GND (not VCC) |
| CDC port not visible | OS driver issue | On Linux, check that the `cdc_acm` kernel module is loaded |

## Experiments

<InArticleAd />


1. **Add a hat switch (D-pad).** Wire four more buttons and add a `uint8_t hat` field to the report struct. A hat switch reports a direction: 0 to 7 for the eight compass directions, or 0x0F for centered. In the report descriptor add `Usage (Hat Switch)` with logical min 0, max 7, and a null state for centered.

2. **Add more analog axes.** Connect a second joystick module to GP28 (ADC2), and use the joystick button pin as ADC input for a third axis, for Rx and Ry (rotation axes). Add Usage 0x33 (Rx) and 0x34 (Ry) to the HID report descriptor: the gamepad becomes a dual-stick controller.

3. **Add force feedback output.** Connect a small vibration motor through a transistor to a PWM-capable GPIO. Add an Output report to the HID descriptor with a usage from the Physical Interface Device (PID) usage page. Implement `tud_hid_set_report_cb()` to read the host's rumble commands and drive the motor PWM accordingly.

4. **Implement button debouncing.** The firmware reads the buttons with no debounce filter. Accept a change only after a button has kept the same state for three consecutive reads at 1 ms intervals, and compare the behaviour before and after, especially with cheap tactile switches that bounce a lot.

## Summary

<InArticleAd />


You built a USB gamepad on the RP2040 with TinyUSB, and it works on Windows, macOS and Linux with no driver of its own. The ideas to keep:

- A USB device answers the host's questions with descriptors, in four levels: device, configuration, interface, endpoint.
- The host asks and the device answers. An interrupt endpoint is one that the host asks at a fixed interval, here every 8 ms.
- A HID report descriptor states what each bit of a report means. The struct in the firmware must match it bit for bit.
- A composite device carries more than one function on one cable, here a gamepad and a debug serial port.
